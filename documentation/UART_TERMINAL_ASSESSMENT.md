# Оценка UART-терминала — без реализации

Историческая оценка. Начиная с версии 0.2.0 реализован
[тест USART1 с DMA и браузерным журналом](USART_CONSOLE.md).

Для стенда полезен небольшой браузерный терминал: ввод HEX/ASCII, непрерывный
журнал RX/TX, временные метки, очистка/пауза отображения, экспорт журнала,
настройки baud/data bits/parity/stop bits и окончания строк CR/LF/CRLF.
Полноценные ANSI/VT100, курсорный экран и эмуляция консоли пока избыточны.

Сложность интерфейса умеренная. Основная работа в прошивке: RX DMA circular
с кольцевым буфером, IDLE/NDTR для границ поступления, отдельная очередь TX,
контроль переполнения/ORE/FE/NE/PE, политика потерянных данных и смена режима
без выдачи ложных байтов. Формат 8N1 при 115200 бод даёт до 11520 байт/с;
за 250 мс это 2880 байт. Поэтому старую схему редкого опроса нельзя бездумно
масштабировать к большим скоростям и большим объёмам данных.

Для небольших ответов допустим HTTP-опрос ограниченными порциями. Для
непрерывного потока предпочтительнее один постоянный WebSocket и ограниченная
очередь в браузере. На MCU всё равно нужны буферы и счётчик переполнений:
остановившийся браузер не должен блокировать USART. Быстрые длительные потоки
потребуют оценки RAM, пропускной способности SPI1/W5500 и, возможно, RTS/CTS.
Браузер отображает данные; точные задержки и временные последовательности
должны исполняться таймерами/DMA MCU.

Разумный следующий этап: выбрать USART и свободные выводы, определить требуемые
скорости и максимальную длину ответа, затем сделать компактный терминал с DMA.
Совместимость с SCPI/LXI для этого не требуется. UART в этой версии не добавлен.

Для первого варианта предпочтителен USART1 с DMA2: DMA1 Stream 3/4 уже заняты
SPI2, а его аварийная процедура может сбросить весь DMA1. Поэтому USART2 на
DMA1 потребовал бы дополнительно пересмотреть эту процедуру. Выводы и baud
выбираются при реализации, сейчас новые порты не заняты.
